PRODUCT OWNER / CURRENT FUNCTIONAL BASELINE

Password-reset requirements and acceptance criteria

REQ-01
A registered user can request a password-reset link using their email address.
AC-01
For a registered email, send a reset link.
AC-02
Release v1
The link expires 30 minutes after issue.
AC-03
A successfully used link cannot be used again.
AC-04
After a successful reset, the new password works and the old password does not.

PRODUCT AND TEST OWNERS / CURRENT INTEGRATION CONTRACT

Reset completion timing

TIM-01

For a valid, unused, unexpired token and an accepted password fixture in the isolated integration environment, reset submission must complete successfully and show a success confirmation within 3,000 ms of submission. The confirmation is created only after a successful reset response. A response/confirmation earlier or later than one second can satisfy this contract. A response error or confirmation after 3,000 ms requires investigation; it must not be normalized away by extending the timeout. This contract does not assert whole-service health, production performance, or email delivery time.

The 30-minute link expiry and the 3,000 ms reset-completion deadline apply to different events. TIM-01 supports the later integration and automation activities; it adds no password policy.

TEST OWNER / CURRENT FIXTURE DESCRIPTION

Integration test setup

DATA-01

Each run creates a distinct registered account, old/new accepted-password fixtures, and a fresh unused token. Submission occurs 60 seconds after token issue. No other test uses this account or token. The negative-policy probe uses a separate fresh fixture. Authentication checks use fresh unauthenticated sessions; cleanup follows each run. Fixture acceptance is test setup evidence, not a general password-policy specification.

Unspecified behaviour and open questions

The baseline leaves these matters unresolved. Record questions rather than inventing expected results.

  • Behaviour for an unregistered email address.
  • Password composition and length rules.
  • Rate limits.
  • Exact behaviour at precisely 30 minutes after link issue.
  • Multiple outstanding reset links.
  • Session invalidation after reset.
  • Email delivery-time guarantees.

For expiry examples, use times clearly before or after the deadline. Keep assertions at the exact boundary pending clarification.
