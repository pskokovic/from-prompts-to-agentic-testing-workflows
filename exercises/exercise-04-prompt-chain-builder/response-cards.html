Reveal instructions

These are authored response-building cards, not a menu of answers. Finish a prompt first. Use the card for your current task, whatever its stage number. If it is first, its input is the current source cards; otherwise use the exact reviewed preceding response. Current source cards remain available at every stage. This gives the same teaching response as the interactive simulation. Copy it verbatim into the worksheet; then review it.

For a linked Output format block, append the source IDs shown in parentheses and place each chosen line as a separate bullet. For a table block, omit all parenthetical source IDs and put each chosen line in its own numbered row under “#” and “Prepared response”. The exact text handoff uses a Markdown table with those two columns. The underlying claims may remain the same; the loss of citations makes review harder. A cited ID may still fail to support the attached claim.

Task: extract supported behaviour and gaps

  1. Registered email → reset link (REQ-01, AC-01).
  2. Link expires 30 minutes after issue (AC-02); a used link cannot be reused (AC-03).
  3. If Input=current and Task=separate: “After reset, new password works and old password does not (AC-04).” Otherwise: “After reset, show a success confirmation.”
  4. If Input=suggestion or Task=complete, add: “Enforce a 12-character minimum (AC-04).” That AC citation does not support the rule.
  5. If Input=current and Task=separate, add: “Open: password policy, exact 30-minute boundary, unregistered email, rate limits, multiple links, sessions, delivery time.” Otherwise: “Open: exact 30-minute boundary; other policy details treated as complete.”
  6. If extraction is not first, add: “This extraction comes after an earlier task; review whether that earlier task relied on unextracted requirements.” If the prior response contains a 12-character claim, add: “The preceding handoff carried a 12-character claim; it still needs product-owner clarification.” If it omits the old-password outcome, add: “The preceding handoff did not state the old-password outcome; check earlier decisions against the credential requirement (AC-04).” Omit that parenthetical ID for the table format.

Task: identify risks

Read the exact reviewed previous response, or current source cards if this task is first. “Inherited policy” means it contains a 12-character minimum/rule/policy. “Missing credential outcome” means it does not mention the old password.

  1. Replay of a successfully used link could permit unintended access (AC-03).
  2. If the old password is mentioned upstream: “Old password remaining valid or new password failing could undermine access control (AC-04).” Otherwise: “Credential outcome is unresolved because the reviewed input omitted the old-password condition.”
  3. If an inherited 12-character claim exists: Input=shortcut gives “A password under 12 characters creates a confirmed policy risk (AC-04).” Input=handoff gives “The inherited 12-character claim needs product-owner clarification before it becomes an oracle.”
  4. Task=likelihood gives “Likelihood: high, based on the supplied material.” Task=impact gives “Impact may be high; likelihood is not measured here.”

Task: propose test ideas

Read the exact reviewed previous response, or current source cards if this task is first. If this task is later, apply the inherited-policy and old-password checks to that text.

  1. Use a fresh valid link, complete reset, and inspect the observable result (REQ-01, AC-01).
  2. If Task=oracles and the old password is mentioned upstream: “In fresh unauthenticated sessions, new password authenticates and old password is rejected (AC-04).” Otherwise: “Success confirmation alone is the credential oracle.”
  3. Attempt to reuse the successfully used link; it must fail (AC-03).
  4. If inherited policy exists: Input=shortcut gives “Reject passwords shorter than 12 characters (AC-04).” Input=handoff gives “Hold the inherited 12-character claim for clarification; no policy oracle yet.”

Review and revision

A readable-only review condition does not test source support. A source-linked response may still contain an unsupported claim. Passing carries the exact response, including flaws; holding stops the chain. On upstream revision, strike through later cards and mark “Needs review”. Rebuild or reaffirm the first affected prompt against the changed input before any revised final proposal.

Comparison checkpoint

After a complete first chain, change an upstream prompt and review its new response. Rebuild and review the first affected downstream response. Compare that response with the same task in the first chain: source support, lost or added claims, and open gaps. A final-output comparison is valid only after every later revised stage is reviewed; complete those stages at home if the live slot ends.
