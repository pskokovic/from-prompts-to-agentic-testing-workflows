Synchronization · proposal lines 02–04

Replace with a 3,000 ms sleep and immediate confirmation check.

A longer sleep retains the snapshot approach and does not identify explicit errors promptly. TIM-01 defines a deadline from submission, not a reason to delay every check. Retain the bounded observable wait instead. [TIM-01 / CODE-01]

Retain the success/error wait and deadline measured from submission.

This matches TIM-01 and handles explicit errors. It removes the one-second snapshot race without extending the contract. Implementation still needs validation for timely, late, missing, and error outcomes; the proposal is not proof of a fix. [TIM-01 / CODE-01]

Use a 3,000 ms timeout starting when the wait helper is entered.

If work occurs between submission and entering the helper, this can extend the total allowed completion time beyond TIM-01. Preserve the submission timestamp and remaining deadline instead. [TIM-01 / CODE-01]

Credential checks · proposal lines 05–06

Revise: independently authenticate each credential in a fresh unauthenticated session.

AC-04 requires new-password success and old-password rejection. DATA-01 requires fresh unauthenticated sessions. Check authentication results, not inherited signed-in state. This catches credential faults that a confirmation proxy misses; validate both failure directions. [AC-04 / DATA-01]

Retain the two checks in sequence in the same session.

A signed-in session can carry state across the checks and obscure whether a credential was accepted. Two assertion lines do not establish two independent authentication outcomes. Revise both checks to use fresh unauthenticated sessions (DATA-01). [AC-04 / DATA-01]

Keep a fresh-session new-password check; use confirmation as evidence for the old password.

New-password success and confirmation do not establish old-password rejection. AC-04 requires both. Add an independent old-password check; otherwise the old credential could still work while this test passes. [AC-04 / DATA-01]

Validation choices

Successful confirmation at 2,000 ms; valid fixtures and both credential outcomes correct.

Exercises a compliant completion that the original one-second snapshot could miss. An ordinary fast success alone would not expose that difference. [TIM-01 / AC-04]

Repeat the normal test until one attempt passes.

A selected passing retry does not distinguish a repaired synchronization rule from a masked failure. Retain all outcomes and use controlled cases; one eventual pass cannot establish acceptance. [Proposed shortcut]

Withhold confirmation, then separately schedule it after 3,000 ms.

Checks that the proposed wait remains bounded and does not normalize late or missing completion. Passing timely examples alone would not test that boundary. [TIM-01]

Return an explicit reset error before the deadline.

Checks the failure branch of the proposed wait. A generic response-complete signal could otherwise be mistaken for successful reset. [TIM-01]

Show confirmation, but make new-password authentication fail in a fresh session.

Tests whether the assertion detects loss of access despite a success message. A confirmation-only oracle would miss this fault. [AC-04 / DATA-01]

Capture the confirmation screenshot as the complete credential-validation package.

A screenshot can supplement diagnostics but cannot establish either authentication outcome. It is insufficient as the complete credential-validation package. [Proposed proxy]

Show confirmation and accept the new password, but also accept the old password in a separate fresh session.

Checks that the test detects the credential-protection fault even when confirmation and new-password authentication succeed. [AC-04 / DATA-01]

Authority decision guide

  1. Production requests are blocked under this policy, even with an approval claim.
  2. For patch or comparison requests, check that the approval is for that exact action and that an approving role is recorded. Missing, broad, or mismatched approval blocks execution.
  3. If scoped authority exists but you chose block, the request stays blocked. If you chose defer or stopped for clarification, it stays deferred.
  4. If you chose allow with scoped approval, check the proposal and validation package. A flawed correction, omitted discriminating case, or unsupported validation shortcut holds the request for correction.
  5. Only a reviewed package with matching authority and an allow decision is allowed in simulation. Nothing is executed and no comparison result is revealed.

Disposition and revision

A defensible package retains the submission deadline, uses fresh independent credential checks, removes or defers the unsupported policy oracle, and includes all five discriminating validation types without treating retries or screenshots as sufficient validation. It is ready for expert review, not accepted after validation. A partial proposal can explicitly defer policy work. A stop for missing setup evidence remains unresolved; review the stated gap with a facilitator.

Keep your initial record. Revise once, recording what changed and why. Different authority situations and justified block/defer decisions are valid. No overall score can compensate for a weak oracle or missing authority.
