ACs · Current functional baseline

Product owner · approved v1

REQ-01: A registered user can request a password-reset link using their email address. AC-01: For a registered email, send a reset link. AC-02: The link expires 30 minutes after issue. AC-03: A successfully used link cannot be used again. AC-04: After a successful reset, the new password works and the old password does not.

Password composition/length, exact behavior at precisely 30 minutes, session invalidation, and delivery-time guarantees remain unspecified.

TIM-01 · Integration timing contract

Product and test owners · current v1

For a valid, unused, unexpired token and an accepted password fixture in the isolated integration environment, reset submission must complete successfully and show a success confirmation within 3,000 ms of submission. The confirmation is created only after a successful reset response. A response/confirmation earlier or later than one second can satisfy this contract. A response error or confirmation after 3,000 ms requires investigation; it must not be normalized away by extending the timeout. This contract does not assert whole-service health, production performance, or email delivery time.

DATA-01 · Fixture description

Test owner · current v1

Each run creates a distinct registered account, old/new accepted-password fixtures, and a fresh unused token. Submission occurs 60 seconds after token issue. No other test uses this account or token. The negative-policy probe uses a separate fresh fixture. Authentication checks use fresh unauthenticated sessions; cleanup follows each run. Fixture acceptance is test setup evidence, not a general password-policy specification.

CODE-01 · Original test snapshot

Test repository · test-t17 · pseudocode

01 test reset_completion:
02   account, token, acceptedNewPassword = isolatedResetFixture()
03   openResetForm(token)
04   submitNewPassword(acceptedNewPassword)  // asynchronous request
05   sleep(1000 milliseconds)
06   assert existsNow("reset-confirmation")
07   cleanup(account)

08 test proposed_password_policy:
09   account, token = separateResetFixture()
10   submitNewPassword("short-example", token)
11   assert result == rejected_because_length_below_12
12   cleanup(account)

existsNow is an immediate snapshot without implicit wait. Diagnostics continue for three seconds after submission even if an assertion fails. The policy probe is a separate test. Cleanup must also run after failures.

Proposal for your review

PROPOSED PATCH · authored AI-response example

01 use the isolated reset fixture from DATA-01
02 start deadline at reset submission
03 wait for successful confirmation, or explicit reset error,
   until submission + 3,000 ms
04 fail on error or if confirmation misses that deadline
05 sign in with the new password; assert signedIn == true
06 in that SAME session, submit the old password;
   assert signedIn == false
07 keep the separate test: reject passwords shorter than 12
08 always clean up fixtures, including after failure

Line numbers belong to this proposal, not CODE-01. It is not an approved implementation. Review its assertions against the sources.

03 / ACT ONLY WITHIN AUTHORITY

Decide authority and disposition

Workshop authority policy

Reading supplied evidence and drafting a proposal are allowed. Applying a test-branch patch or running an isolated comparison requires approval from the designated automation reviewer for that action and scope. Neither grants merge or production access. Production changes and changes intended to hide failures are prohibited.

Approval cards below are hypothetical workshop records, not real authorization. Your selection defines the situation to review. Nothing is applied or run, even when allowed in the simulation.

Ready for review ≠ authorized to execute ≠ accepted after validation. This activity does not execute validation or establish acceptance. Text is checked for presence only; a person must review its meaning.
