EXERCISE 02 / TAKE-HOME EXAMPLE

One defensible package

Read after making your first decisions. This is authored fictional teaching material, not a real model response or proof of participant competence. Equivalent justified answers are acceptable.

Included evidence

REQ-01: A registered user can request a password-reset link using their email address.

  • AC-01: For a registered email, send a reset link.
  • AC-02 · Release v1: The link expires 30 minutes after issue.
  • AC-03: A successfully used link cannot be used again.
  • AC-04: After a successful reset, the new password works and the old password does not.

Authority: product owner, current functional baseline v1. These sources define the requested behaviour and expected results.

Other source decisions

  • AC-02 (release v0) — exclude: superseded release v0. It conflicts with the current expiry rule. Alternatively, retain it explicitly as history, never as a second expected result.
  • TIM-01 — defer: a valid integration timing contract for later synchronization review; unnecessary for this minimal functional package. A scoped inclusion can be justified if its purpose is explained.
  • CI-01 — defer: a failed snapshot belongs in later failure investigation; observations cannot define requirements.
  • NOISE-01 — exclude: the export issue concerns a different feature.
  • SUGGEST-01 — exclude: no approved source supports a 12-character rule. Raise password policy for clarification.

Two short reasons for the timed activity

  1. AC-02 (release v0): Exclude because AC-02 (release v1) supersedes its 15-minute rule.
  2. CI-01: Defer because this run is an observation for diagnosis, not a functional oracle.

The longer source-by-source rationale above is for review afterward; participants need only write two short reasons during the activity.

Conflict and questions

AC-02 (release v1) supersedes AC-02 (release v0): expiry is 30 minutes, not 15. No source settles the exact behaviour at precisely 30 minutes.

  1. What response and observable behaviour are required for an unregistered email?
  2. Is a token accepted or rejected at exactly 30 minutes, and how is that boundary measured?

Other valid gaps include password composition/length, multiple outstanding links, rate limits, session invalidation, and delivery-time guarantees.

Prepared test-design excerpt

  • Request using a registered email → send a reset link. [REQ-01, AC-01]
  • Use an unused token at 31 minutes → reject it as expired. [AC-02 · Release v1]
  • Reuse a successfully used link → reject reuse. [AC-03]
  • After a successful reset, check authentication in fresh sessions → new password succeeds and old password fails. [AC-04]

These are representative conditions, not a complete test suite. Exact-boundary and password-policy oracles remain pending clarification.

Compare with a weak package

A package that treats AC-02 (release v0) as an active rule alongside AC-02 (release v1) offers incompatible expiry expectations. Including the AI suggestion risks turning a plausible policy into an unsupported oracle. Adding an export issue does not repair missing reset requirements. More context alone does not improve the evidence.

Self-review

Check whether each source serves this task, whether its status and scope support the use you chose, and whether your expiry sentence names the current rule. Different source counts can be justified.

Questions about unregistered-email behaviour, the exact 30-minute boundary, password policy, and rate limits remain open. “Is expiry 15 or 30 minutes?” and “Can a successfully used link be reused?” are answered by AC-02 (release v1) and AC-03, respectively.
