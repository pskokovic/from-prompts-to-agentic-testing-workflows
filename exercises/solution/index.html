Exercise Solutions

Compare your reasoning with these worked answers after attempting each exercise. They explain the choices, the evidence behind them, and what remains open. Other answers can be defensible when their reasoning fits the sources.

All scenarios and results are fictional teaching material. The exercises use local simulations, not connected AI or real test execution. A strong prompt, an approved action, and a validated change are separate judgments.

Choose an exercise

  1. Prompt Lab — make the task reviewable
  2. Context Lab — select sources for the task
  3. Evidence Challenge — investigate a claim

EXERCISE 01

Prompt Lab

What you practise: turn a broad request into a specific, grounded task with a reviewable output.

A defensible selection

Choose a relevant role, Derive reviewable test conditions, REQ-01, the current AC-01–04 (release v1), a table of conditions and expected results, coverage and open questions, functional scope, no invented requirements, explicit assumptions/questions, and a source reference for each condition. A descriptive heading is optional.

Leave out the superseded expiry authority, gap-filling as fact, the definitive-answer instruction that hides questions, and the summary-only instruction that removes review detail. Selecting every option introduces conflicting instructions.

Example prompt

Act as a software tester. Derive reviewable functional test conditions
for password reset using REQ-01 and the current AC-01–04, release v1.

Return a table with condition, expected result, and supporting source ID.
Add a coverage summary and open questions. Do not invent requirements.
Separate assumptions and proposals from supported expected results.
Use the supplied source text below as the functional baseline.

REQ-01: A registered user can request a password-reset link using their email address.
AC-01: For a registered email, send a reset link.
AC-02 · Release v1: The link expires 30 minutes after issue.
AC-03: A successfully used link cannot be used again.
AC-04: After a successful reset, the new password works and the old password does not.
Representative supported test conditions
ConditionExpected resultSource
Request reset for a registered email.A reset link is sent.REQ-01, AC-01
Attempt to use an unused link at 31 minutes.It is rejected as expired.AC-02 · Release v1
Reuse a successfully used link.Reuse is rejected.AC-03
Authenticate after successful reset.The new password works; the old password does not.AC-04

Why this works

The task, evidence, scope, output, and review rules are explicit. Each expected result can be checked against its source. “Reject passwords shorter than 12 characters” has no approved source and must remain a policy question, not a test oracle.

Still open: exact behaviour at precisely 30 minutes, unregistered-email behaviour, password policy, and other unspecified conditions. These examples are not a complete test suite. A maximum simulation score measures selected prompt features; it does not guarantee correctness.

Learning point: a better prompt makes an answer easier to review; it does not replace review.

EXERCISE 02

Context Lab

What you practise: decide which sources should support functional password-reset test design now.

One defensible source package
SourceDecisionReason
REQ-01IncludeCurrent requirement defining the feature and user action.
AC-01–04 · Release v1IncludeCurrent expected functional behaviour, including the 30-minute expiry.
AC-02 · Release v0ExcludeThe 15-minute rule was superseded. It cannot govern the current expected result.
TIM-01DeferRelevant to later integration timing and synchronization review; unnecessary for this minimal functional package.
CI-01DeferA recorded failure belongs in later investigation. An observation does not define a requirement.
NOISE-01ExcludeThe export-column issue concerns another feature.
SUGGEST-01ExcludeThe proposed 12-character minimum is unreviewed and unsupported by approved requirements.

Example answer record

Expiry conflict: “AC-02 release v1 supersedes release v0: the current expiry rule is 30 minutes, not 15.”

Two short reasons: “Exclude release v0 because it is superseded.” “Defer CI-01 because it is evidence for diagnosis, not a functional oracle.”

Two unresolved questions: “What should happen for an unregistered email?” “Is a token accepted or rejected at exactly 30 minutes, and how is that boundary measured?”

Acceptable variations

TIM-01 can be included with an explicit integration-timing purpose. Release v0 can be retained as clearly marked history. Neither choice may override the current functional baseline. Password policy, rate limits, or multiple outstanding links are also valid unresolved questions.

Connection to the next exercise: CI-01 was postponed because the task was functional test design. When the task becomes failure investigation, the same source becomes relevant evidence.

Learning point: grounding depends on source authority, version, scope, and relevance to the current task.

EXERCISE 03

Evidence Challenge

What you practise: review the claim “The password-reset service is unstable” without turning a failed assertion into a confirmed diagnosis.

The five supplied observation choices
ChoiceSelect?Explanation
CI-01: confirmation absent at the 1,002 ms snapshot.YesThis is the recorded observation.
HIST-01 independently corroborates the same captured CI events.NoThe report derives from those events; it is another presentation of the evidence.
CODE-01: fixed 1,000 ms sleep followed by an immediate existence check.YesThe code supplies a possible mechanism for checking too early.
CI-01 proves that the password reset failed.NoAbsence at that moment does not establish the final reset outcome.
HIST-01: supplied runs fail when confirmation is later than the snapshot.YesThe sample shows a timing/outcome association, not the cause of timing variation.

One defensible decision record

  • Claim decision: Investigate.
  • Provisional category: Test synchronization.
  • Preferred hypothesis: The test checks before a valid confirmation appears.
  • Competing hypothesis: The reset genuinely fails or exceeds its applicable completion bound.
  • Evidence and limit: The snapshot was empty, the check is immediate, and the history associates later confirmation with failure. This does not establish service instability.
  • What would weaken the preferred hypothesis: A matching capture showing a reset error, confirmation before the failed snapshot, or completion beyond the accepted bound.
  • Next action: Request TIM-01 to establish the applicable timing expectation.

Revision after TIM-01

“Keep investigate. TIM-01 specifies successful completion and confirmation within 3,000 ms of submission. The supplied history timings fit that bound, but the raw correlated run-204 capture and cause of latency remain unresolved.” This does not establish either AC-04 authentication outcome.

Acceptable variations

You can reject the claim's certainty while retaining instability as a hypothesis. That is not a finding that the service is healthy. Requesting TRACE-01 to correlate run 204/request reset-204 is also defensible; in Exercise 3 it remains pending for Exercise 6. If you already read TIM-01 in Exercise 2, cite it as prior knowledge.

Your decision record captures your observations, judgment, hypotheses, evidence limits, next action, and revision. It can become reviewed context for later work if copied onward with its source links and uncertainty. It is not automatically a prompt or persistent memory.

Learning point: distinguish what happened, what it might mean, and what evidence could change your judgment.

EXERCISE 04

Prompt Chain Builder

What you practise: build three focused prompts and review each output before it becomes the next prompt's input.

Supported behaviour and gaps → Review → Risks → Review → Test ideas and expected results

A defensible prompt configuration and review
StageChoose these blocksReview before passing
ExtractCurrent sources; separate supported behaviour from gaps; source-linked list; source-support review.REQ-01 and AC-01–04 support the stated behaviours. AC-04 includes both credential outcomes. Policy and exact expiry boundary remain open.
Identify risksReviewed handoff plus current cards; plausible impacts with unknown likelihood; source-linked list; inherited-claim review.Used-link replay relates to AC-03. Old-password acceptance or new-password failure relates to AC-04. No measured likelihood is supplied.
Propose testsReviewed handoff plus current cards; observable oracles including both AC-04 outcomes; source-linked list; oracle review.Include independent fresh-session credential checks and used-link replay. A success confirmation alone does not establish credential protection.

Example final proposal

  1. Use a fresh valid link, complete the reset, and inspect the observable result. [REQ-01, AC-01]
  2. Check in fresh unauthenticated sessions: the new password authenticates and the old password is rejected. [AC-04]
  3. Attempt to reuse the successfully used link; reuse must fail. [AC-03]

The exercise limits the proposal to a small set of ideas. Expiry checks before and after 30 minutes are a valid extension; the exact boundary remains unresolved.

What to do with a weak handoff

If extraction invents a 12-character rule, revise and rerun or hold the handoff. AC-04 written beside that rule does not support it. A review note does not edit the response: passing sends the exact response text onward, including any flaws.

Compare the first and revised chain

Keep the first chain. Change the first stage, review the new output, and rerun/review the first affected downstream stage. Compare source support, missing credential outcomes, and preserved gaps. Later outputs stay Needs review until checked against the new handoff. Completing all remaining stages allows a full final-output comparison.

All six task orders are allowed. The default extraction → risks → tests order makes dependencies easiest to follow. Another order needs an explanation of what input arrived late. “First”, “revised”, “neither ready”, or “no clear advantage” can be justified by the actual outputs.

Learning point: the next prompt receives the output you pass, not the correction you intended.

EXERCISE 05

Automation Review, Tools and Permissions

What you practise: separately judge a proposed test change, its validation plan, and authority for a specific action.

Review of the proposed correction
ConcernDefensible treatmentWhy
SynchronizationRetain the observable success/error wait, with a deadline measured from submission.TIM-01 supports a bounded 3,000 ms wait. Avoid a one-second snapshot race without extending the contract.
Credential checksRevise: test each password independently in a fresh unauthenticated session.AC-04 requires both outcomes; DATA-01 avoids carried signed-in state masking the result.
Password policyRemove the unsupported assertion and retain the question, or defer the policy test pending approval.The supplied sources do not establish a 12-character minimum. Accepted fixtures are not a general policy specification.

A discriminating validation plan

Specify a delayed valid success and two distinct fault cases. For example, select missing/late confirmation and old-password acceptance. Other pairs below are valid; unchosen cases remain outstanding.

Expected results and evidence to retain
CaseExpected test outcomeUseful observation
Valid success delayed to 2,000 msPass only when confirmation and both credential checks meet the sources.Submission/confirmation times and separate authentication results.

Authority depends on your assigned card

Reference authority decisions after a sound proposal review
CardDecisionExplanation
AAllow the named test-only patch action.The review-ready proposal and approval scope match. This does not authorize a comparison run or production access.
BDefer pending matching approval.The request is an isolated comparison, but the approval covers only applying a patch to a test-only branch. A justified block of the current unmatched request is also defensible.

Example revision: “I replaced the same-session checks with separate fresh-session checks. I retained the bounded wait and deferred the unsupported policy assertion.” Explain the source basis of whichever change you actually made.

Final status: ready for expert review if the proposal is sound; validation still required. No checks execute here, so accepted after validation remains no. Actual results, fixture/session evidence, diagnostics, remaining fault cases, policy clarification, and human review are still needed.

Learning point: technical quality, permission, and acceptance after validation are separate judgments.

EXERCISE 06

Loop Workshop

What you practise: design a controlled investigation loop for runs 204, 208, and 209. New observations should affect the next action while evidence, permissions, state, and a shared budget remain explicit.

One valid block sequence

  1. Define goal and instructions.
  2. Select context and sources.
  3. Initialize workflow state.
  4. Assess observations.
  5. Choose the next action.
  6. Check permissions and limits.
  7. Execute tool call.
  8. Validate tool output.
  9. Update workflow state.
  10. Check stopping conditions.
  11. Request human review.

Connect continue back to Assess observations, retaining the queue, per-run evidence, gaps, and attempts consumed. The first three setup blocks may be reordered. The eleven-block decomposition and return target are this exercise's teaching model, not a universal agent architecture.

Leave out Use every successful response, Repeat until the test is green, and Apply the fix to production. Optional Add version context belongs after state update and before stopping checks. CHANGE-01 is not retrieved on these routes and covers only runs 201–205; it cannot explain the entire batch.

One defensible configuration
ControlChoice and reason
PriorityRisk first: 208 → 209 → 204. Investigate credential protection and the deadline breach before the snapshot race.
Evidence admissionValidate source, run/request identity, timing basis, scope, and errors before updating that case.
Completion thresholdPer-run triage plus an approved run-204 comparison where matching evidence is available.
Invalid evidenceEscalate the affected run, preserving its gap; continue other independent cases.
AuthorityCheck scoped approval before the isolated comparison. Read access does not authorize changes or release.
Budget and returnFour shared execution attempts; return to assessment with updated state.
Human handoffName a reviewer and explain the priority, stopping policy, remaining uncertainty, and next owners.

Normal situation: expected report

Three capture retrievals investigate 208, 209, and 204; the fourth attempt performs the approved simulated run-204 comparison. The ending is Recommendation ready, with the following bounded findings.

Per-run conclusions after matching evidence
RunSupported provisional findingEvidence, limits, and next owner
204Likely test synchronization issue.TRACE-01 places the 1,002 ms snapshot before the 1,460 ms confirmation, within TIM-01. VALID-01 illustrates a discriminating comparison when approved. Automation reviewer: implement and validate bounded synchronization and AC-04 assertions. Actual patch validation and underlying latency cause remain unresolved.
208Observed AC-04 violation.TRACE-208 shows both passwords accepted in separate fresh sessions after reset. Product/security owner: investigate credential invalidation promptly. Root cause and production exposure are unknown.
209Observed TIM-01 breach.TRACE-209 shows confirmation at 3,200 ms, beyond the 3,000 ms bound. Service owner: investigate latency without extending the requirement. Credential behaviour and latency cause are unknown.

These observations do not establish three distinct root causes. A comparison for run 204 cannot close 208 or 209. VALID-01 is prepared simulation evidence, not a verified real fix or a whole-service health assessment.

Other valid routes and endings

How changed evidence and limits should change the outcome
SituationDefensible response
Queue coverage; bounded triage only204 → 208 → 209 costs three retrieval attempts. Report provisional findings and remaining validation. Explain the priority trade-off.

Example reflection

“I prioritize credential-protection evidence, validate each result's identity, and keep separate case state. Missing evidence changes the route to escalation rather than a guessed diagnosis. A bounded stop preserves the partial report. Model judgment may help interpret varied evidence and choose follow-ups; the harness must enforce permissions, identity checks, and execution limits.”

The simulator's authored policies do not demonstrate live AI behaviour. A justified escalation or limit stop can be a correct controlled outcome even when the investigation is incomplete.

Learning point: a useful loop changes its next action with the evidence and knows when to stop.

Carry the learning into your own work

Define the task → select its sources → review the evidence → review each handoff → challenge a proposed change → control the investigation loop.

For any answer, ask: What supports it? What remains unknown? What observation could change it? Who may authorize the next action? What must be checked before acceptance?
