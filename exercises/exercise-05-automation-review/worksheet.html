ACs · Current functional baseline

Product owner · approved v1

REQ-01: A registered user can request a password-reset link using their email address. AC-01: For a registered email, send a reset link. AC-02 (release v1): The link expires 30 minutes after issue. AC-03: A successfully used link cannot be used again. AC-04: After a successful reset, the new password works and the old password does not.

Password composition/length, exact behavior at precisely 30 minutes, session invalidation, and delivery-time guarantees remain unspecified.

TIM-01 · Integration timing contract

Product and test owners · current v1

For a valid, unused, unexpired token and an accepted password fixture in the isolated integration environment, reset submission must complete successfully and show a success confirmation within 3,000 ms of submission. The confirmation is created only after a successful reset response. A response/confirmation earlier or later than one second can satisfy this contract. A response error or confirmation after 3,000 ms requires investigation; it must not be normalized away by extending the timeout. This contract does not assert whole-service health, production performance, or email delivery time.

DATA-01 · Fixture description

Test owner · current v1

Each run creates a distinct registered account, old/new accepted-password fixtures, and a fresh unused token. Submission occurs 60 seconds after token issue. No other test uses this account or token. The negative-policy probe uses a separate fresh fixture. Authentication checks use fresh unauthenticated sessions; cleanup follows each run. Fixture acceptance is test setup evidence, not a general password-policy specification.

2 · Plan three validation cases

Delayed valid success

With valid DATA-01 fixtures, reset succeeds and confirmation appears 2,000 ms after submission. New-password sign-in succeeds and old-password sign-in fails, each in a fresh unauthenticated session.

  • □ Pass after both credential checks; retain submission, confirmation, and authentication observations.
  • □ Fail because confirmation came after the original one-second snapshot.

Choose two different faults and one expected outcome/evidence for each:

□ Missing or late confirmation

Keep confirmation absent, or create it only after 3,000 ms from submission. [TIM-01]

  • □ Fail at the submission deadline; retain submission/confirmation times and diagnostics.
  • □ Extend the wait and pass when confirmation eventually appears.

□ Explicit reset error

Return an explicit reset error before the deadline; no successful reset occurs. [TIM-01]

  • □ Fail and retain the error and timing evidence.
  • □ Pass because the request completed before 3,000 ms.

□ New password fails

Show confirmation, but make new-password authentication fail in a fresh session. [AC-04 / DATA-01]

  • □ Fail the new-password assertion; retain the fresh-session authentication result.
  • □ Pass because a success message appeared.

□ Old password still works

Show confirmation and accept the new password, but also accept the old password in a separate fresh session. [AC-04 / DATA-01]

  • □ Fail the old-password rejection assertion; retain the fresh-session authentication result.
  • □ Pass because confirmation and new-password sign-in succeeded.
