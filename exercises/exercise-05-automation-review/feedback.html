Synchronization · proposal lines 02–04 · TIM-01 / CODE-01

Replace it with a 3,000 ms sleep and immediate check.

A longer fixed sleep remains an immediate snapshot and does not handle explicit errors promptly. TIM-01 defines a deadline, not a required wait duration.

Retain the success/error wait with the deadline measured from submission.

TIM-01 supports an observable bounded wait from submission. It can avoid CODE-01’s one-second snapshot race without extending the contract. The implementation still needs validation.

Start a fresh 3,000 ms timeout when the wait helper begins.

Starting the clock after submission could extend the allowed completion time beyond TIM-01. Preserve the submission timestamp.

Credential checks · proposal lines 05–06 · AC-04 / DATA-01

Retain both checks in sequence in the same session.

Two assertion lines in one signed-in session do not establish two independent authentication outcomes. Use fresh unauthenticated sessions.

Revise: check each password independently in a fresh unauthenticated session.

AC-04 requires both outcomes; DATA-01 requires fresh unauthenticated sessions. Carried signed-in state can hide whether the old credential still works.

Check only the new password; treat confirmation as evidence for the old one.

A confirmation and new-password success do not prove the old password is rejected. AC-04 requires an independent old-password check.

Password policy · proposal line 07 · Current ACs / DATA-01

Defer the policy test and request an approved policy; continue supported reset checks.

No supplied source defines a length threshold. Deferral keeps the policy question visible without making an invented oracle authoritative.

Change the minimum length from 12 to eight characters.

A familiar threshold is still invented. Neither the current ACs nor DATA-01 approves an eight-character rule.

Remove the unsupported assertion and track policy coverage as an open question.

Removal avoids a false defect claim while preserving the need for a product-owner clarification.

Validation outcomes

Delayed valid success

Pass after both credential checks; retain submission, confirmation, and authentication observations. Two seconds is within TIM-01’s submission-based limit. The full test passes only when both AC-04 credential outcomes hold.

Fail because confirmation came after the original one-second snapshot. The original snapshot is the weakness under review; TIM-01 permits this delayed success.

Missing or late confirmation

Fail at the submission deadline; retain submission/confirmation times and diagnostics. This tests the documented bound and keeps a late or missing result visible.

Extend the wait and pass when confirmation eventually appears. Extending the bound would normalize a TIM-01 breach.

Explicit reset error

Fail and retain the error and timing evidence. A completed error response is not successful reset confirmation.

Pass because the request completed before 3,000 ms. TIM-01 requires success, not merely a completed response.

New password fails

Fail the new-password assertion; retain the fresh-session authentication result. This fault violates AC-04 even though confirmation appeared.

Pass because a success message appeared. Confirmation alone cannot establish the new credential works.

Old password still works

Fail the old-password rejection assertion; retain the fresh-session authentication result. This detects the credential-protection fault even when the new password works.

Pass because confirmation and new-password sign-in succeeded. AC-04 also requires the old password to stop working.

Two deliberately faulty cases complete the classroom task. The unchosen faults, actual execution results, fixture/session evidence, diagnostics, and policy clarification stay outstanding for later acceptance.

Assigned authority cards

Card A has matching scope for a test-branch patch, but unresolved technical concerns can still hold it. Card B's patch approval does not authorize a comparison run; defer for matching approval or block the current request with that reason. Card C requests prohibited production action and must be blocked. A matching record never grants merge or production authority and does not make a patch correct.

Keep the initial review, then revise once. Ready for review, authorized to execute, and accepted after validation are separate. This activity cannot establish the last state or diagnose run 204.
